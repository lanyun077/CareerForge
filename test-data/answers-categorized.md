## specific / 具体回答（10 条）

s1. 该项目用 Flask 和 MySQL 实现，我负责订单与库存模块。订单列表接口出现慢查询，我通过 EXPLAIN 定位到全表扫描，添加 (user_id, created_at) 联合索引并改为游标分页后，响应时间从 800ms 降到 120ms，用 ab 压测 1000 次请求验证了结果。
s2. 索引底层是 B+ 树，叶子节点存数据并按键有序排列，等值和范围查询都能走索引；对列使用函数、前缀通配 LIKE、隐式类型转换或违反最左前缀时索引失效。我在项目里用 EXPLAIN 确认过一次类型转换导致索引失效的问题。
s3. 排查思路分四步：先看监控确认是数据库还是服务本身的问题；再查慢查询日志定位具体 SQL；然后加索引或引入 Redis 缓存；最后用压测对比优化前后的 P95 响应时间验证效果。我在项目中用这套方法把一个 2s 的接口优化到 300ms。
s4. 防重复提交我用 Redis 实现幂等令牌：客户端先请求 token，提交时带 token，服务端用 Lua 脚本原子性地校验并删除，删除成功才执行业务。压测 500 并发下零重复落库。
s5. 项目部署在 2 核 4G 的 Linux 服务器上，Nginx 反向代理 + Gunicorn 4 worker，数据库和应用的 QPS 峰值约 1200，接口平均响应 90ms，已稳定运行 6 个月，期间通过日志监控发现并修复过一次内存泄漏。
s6. 分歧背景是队内对接口返回格式有分歧：一方要 RESTful 风格，一方想统一包一层状态码。我整理了两种方案对前端调用成本的对比示例，拉齐了一次 30 分钟的评审，最终采用 RESTful + 错误码头部的折中方案，项目按时上线。
s7. 单元测试用 pytest 编写了 47 个用例，覆盖订单创建、库存扣减、超时回滚等核心路径，核心模块覆盖率 88%，CI 里每次提交自动跑，上线前还发现过一个边界条件下库存为负的 bug。
s8. 缓存一致性采用延迟双删：先删缓存、更新数据库、延迟 500ms 再删一次，配合过期时间兜底。商品详情接口缓存命中率 96%，数据库 QPS 从 3000 降到 400，没有再出现过脏读投诉。
s9. 今天最有信心的是项目经历部分，慢查询优化的数据都是我亲手测的；需要提升的是高并发场景的系统性设计，比如限流和降级策略，我计划接下来学习相关内容并做一个压测实验。
s10. GIL 是 Python 的全局解释器锁，同一时刻只允许一个线程执行字节码，所以 CPU 密集任务多线程无法并行。我在数据清洗脚本里改用 multiprocessing 多进程，处理 5 万条数据的时间从 40 分钟降到 12 分钟。
