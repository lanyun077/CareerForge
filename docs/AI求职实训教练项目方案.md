# AI求职实训教练项目方案

> 版本：MVP 方案 v1.0
>
> 项目性质：AI+软件创新赛参赛作品
>
> 当前原则：拿奖优先、稳定演示优先、先做出完整闭环，再考虑扩展

## 一、项目概述

### 1.1 项目名称

暂定名称：**AI求职实训教练**

原始名称“全流程求职模拟器”容易让人理解为覆盖所有行业、所有岗位和完整招聘流程，首版实际无法承担这么大的范围。因此，参赛作品建议使用更准确的名称，突出“训练”和“复盘”，避免夸大产品能力。

### 1.2 一句话定位

面向计算机专业学生的 AI 求职训练与复盘系统，根据目标岗位、用户简历和面试回答组织针对性训练，并将问题转化为下一轮可执行的改进建议。

### 1.3 目标用户

- 正在准备实习或校招面试的计算机专业学生。
- 缺少面试练习对象的学生。
- 想针对一个具体岗位反复训练、比较进步情况的求职者。

### 1.4 核心痛点

目标用户通常存在以下问题：

- 不知道自己的简历是否匹配目标岗位。
- 项目经历写得比较空泛，面试时难以讲清楚。
- 只能练习固定题目，无法应对面试官追问。
- 面试结束后只知道“表现不好”，不知道具体差在哪里。
- 得到建议后没有再次训练和验证改进效果的机制。

### 1.5 项目核心价值

本项目不是让 AI 陪用户聊天，也不是简单生成面试题，而是建立一个可重复的训练闭环：

```text
岗位要求
  + 用户简历
  + 用户回答
      ↓
AI组织针对性面试
      ↓
基于证据的能力分析
      ↓
明确的改进建议
      ↓
新的专项挑战
      ↓
前后表现对比
```

## 二、范围与默认假设

### 2.1 首版岗位范围

建议首版只支持一个岗位族：**Python 后端开发实习生**。

选择该岗位的理由：

- 职位要求容易整理成结构化配置。
- 面试内容可以围绕 Python、数据库、接口、项目经历设计。
- 简历、面试问题和测试回答容易自行构造。
- 后续可以扩展到 Java 后端、前端和数据分析岗位。

如果团队最终不熟悉 Python，可以将岗位改为“软件开发实习生”，但这会增加评分主观性，降低技术结果的可信度。岗位方向需要在开发前最终确认，不能同时支持多个岗位。

### 2.2 首版产品边界

首版要完成以下核心流程：

```text
选择目标岗位
→ 输入或上传简历
→ AI分析岗位匹配和简历缺口
→ 进行文字模拟面试
→ 根据简历和回答进行有限追问
→ 生成结构化复盘报告
→ 根据薄弱项生成第二次挑战
→ 对比两次训练结果
```

首版不承诺：

- 预测用户真实录取概率。
- 替代真实 HR 或技术面试官。
- 判断用户的真实情绪、紧张程度或诚信程度。
- 评价与岗位能力无关的性别、年龄、地域、学校等信息。
- 覆盖所有行业和职位。

## 三、MVP功能设计

### 3.1 岗位配置

首版内置一个岗位模板，包含：

- 岗位名称。
- 岗位职责。
- 必备技能。
- 加分技能。
- 常见项目类型。
- 面试阶段。
- 评分维度和评分规则。
- 预设面试问题。

建议暂时不做真实公司数据和多家公司选择。可以使用一个虚拟招聘场景，例如“互联网公司 Python 后端开发实习生岗位”，并明确说明该岗位为模拟岗位，不代表任何真实公司的招聘标准。

### 3.2 简历输入与分析

首版支持两种输入方式：

1. 直接粘贴简历文本。
2. 上传文本型 PDF 文件。

PDF 解析失败时，必须允许用户直接粘贴文本，不能让文件解析成为流程阻塞点。

简历分析输出包括：

- 教育经历、项目经历、技能和成果等结构化信息。
- 与目标岗位的匹配情况。
- 已具备的技能。
- 岗位要求中缺失的技能或证据。
- 空泛表述、重复内容和缺少量化结果的描述。
- 三条优先级明确的修改建议。

分析结果不能只有一段长文本，必须结构化展示。例如：

```text
岗位要求：熟悉数据库优化
简历现状：使用过 MySQL
问题：没有说明数据规模、优化方法和结果
建议：补充索引设计、慢查询优化以及响应时间变化
证据：简历中的“订单系统项目”段落
```

### 3.3 模拟面试

面试流程由程序控制，建议固定为：

```text
自我介绍
→ 项目经历
→ 技术问题
→ 场景问题
→ 行为问题
→ 总结
```

一次面试控制在 5—7 个问题，每个问题最多追问 1 次。程序负责维护当前阶段、问题数量、已问问题和结束条件；大模型只负责在限定范围内生成问题、追问和分析。

首版以文字回答为主，保证用户可以完整跑通一次面试。

### 3.4 针对性追问

追问必须根据以下信息生成，不能完全随机：

- 目标岗位要求。
- 用户简历中的具体项目或技能。
- 用户当前回答。
- 用户回答中缺少的事实、过程、结果或证据。
- 用户前后回答是否一致。
- 已经问过的问题。

合格的追问至少满足以下一个条件：

- 针对简历中的具体项目。
- 针对回答中的模糊表述。
- 针对用户没有提供证据的结论。
- 针对前后回答不一致的地方。
- 针对岗位要求中尚未验证的能力。

示例：

```text
用户回答：我负责了系统后端开发。

普通追问：你使用了哪些技术？

针对性追问：你具体负责哪个模块？这个模块遇到过什么问题？你如何验证解决方案有效？
```

### 3.5 复盘报告

报告至少包含：

- 简历与岗位匹配情况。
- 表达结构评分。
- 回答具体性评分。
- 岗位相关性评分。
- 项目证据完整度评分。
- 技术回答完整度评分。
- 主要失分原因。
- 用户回答中的具体证据片段。
- 下一轮训练建议。
- 推荐的专项挑战。

报告应使用“模拟表现分”“岗位准备度”等表达，不使用“录取概率”“拿 Offer 概率”等缺乏真实数据支持的表达。

### 3.6 再次挑战

再次挑战不能只是重复同一套题。系统应根据上一轮报告中的薄弱项生成新的问题，例如：

- 项目描述不具体：生成项目细节追问。
- 缺少量化结果：生成结果和指标追问。
- 技术原理不完整：生成基础原理题。
- 场景回答缺少结构：生成新的场景题。

两次训练应展示以下变化：

- 各评分维度变化。
- 主要问题是否得到改善。
- 新一轮仍然存在的问题。
- 下一步训练建议。

## 四、评分设计

### 4.1 评分原则

不能让大模型直接输出一个无法解释的总分。评分必须由固定维度、明确规则和回答证据组成。

建议评分维度：

| 维度 | 权重 | 评价重点 |
|---|---:|---|
| 表达结构 | 25% | 是否有清晰的背景、任务、行动和结果 |
| 回答具体性 | 25% | 是否包含具体职责、方法、数据和结果 |
| 岗位相关性 | 20% | 是否回答了目标岗位真正关心的能力 |
| 项目证据 | 20% | 是否能证明用户确实参与并理解项目 |
| 技术完整度 | 10% | 技术概念、原理和方案是否基本完整 |

最终得分由后端按照固定公式计算，大模型只输出每个维度的评分建议、理由和证据。

### 4.2 评分结果格式

模型应输出类似以下结构化结果：

```json
{
  "dimensions": [
    {
      "name": "回答具体性",
      "score": 3,
      "maxScore": 5,
      "evidence": "使用了MySQL，但没有说明数据规模和优化结果",
      "suggestion": "补充具体数据量、优化方法和性能变化"
    }
  ],
  "followUpReason": "用户提到数据库，但没有提供实际优化证据",
  "confidence": "medium"
}
```

后端要校验分数范围、字段完整性和 JSON 格式。解析失败时自动重试一次，仍然失败则使用备用评分结果，不允许页面直接崩溃。

## 五、AI与软件架构

### 5.1 总体架构

```text
Web前端
├─ 岗位选择
├─ 简历输入与分析
├─ 模拟面试
├─ 面试过程记录
├─ 复盘报告
└─ 两次训练对比

应用后端
├─ 岗位配置服务
├─ 简历解析服务
├─ 面试状态机
├─ 追问生成服务
├─ 评分服务
├─ 报告生成服务
└─ 训练记录服务

AI能力
├─ 简历信息抽取
├─ 岗位匹配分析
├─ 面试问题生成
├─ 追问生成
├─ 回答评分建议
└─ 复盘建议生成
```

### 5.2 技术路线建议

在没有现成基础、主要依靠 Agent 开发的前提下，建议采用单体 Web 应用，避免前后端使用多套技术。

建议技术栈：

- 前端：Next.js + TypeScript。
- 样式：Tailwind CSS。
- 后端：Next.js Route Handlers。
- 数据库：Supabase 或 PostgreSQL。
- 文本解析：PDF 文本提取，失败时支持复制粘贴。
- 大模型：封装为统一的 OpenAI-compatible API。
- 语音：独立封装 ASR 接口，作为可选能力。
- 部署：可访问的 Web 演示环境。

不建议首版同时引入 React、FastAPI、Spring Boot、向量数据库、消息队列和多个模型服务。固定岗位和小型题库不需要复杂 RAG，先使用结构化岗位配置和题库即可。

## 六、稳定性与降级方案

“能稳定演示”是本项目的第一工程目标。

### 6.1 固定流程控制

程序控制以下内容：

- 当前面试阶段。
- 问题总数。
- 每题追问次数。
- 已经问过的问题。
- 面试结束条件。
- 报告生成时机。

大模型不得直接控制整个流程。

### 6.2 固定题库兜底

每个阶段准备 3—5 个基础问题。模型调用失败时，可以使用固定题库继续面试。

### 6.3 演示数据兜底

系统内置一个演示账号或演示案例，包括：

- 示例简历。
- 示例面试回答。
- 示例追问。
- 示例复盘报告。
- 示例二次挑战结果。

演示数据不能冒充真实用户数据，应标记为“演示案例”或“内部测试案例”。

### 6.4 输入方式降级

```text
录音输入
→ 语音转文字失败
→ 切换文字输入

PDF解析失败
→ 提示用户复制粘贴简历文本

大模型调用失败
→ 重试一次
→ 使用固定问题或备用结果
```

## 七、语音功能方案

语音功能可以作为演示增强，但不能成为主流程的依赖。

建议实现：

```text
浏览器录音
→ 上传音频
→ ASR转文字
→ 使用文字进入原有面试流程
```

暂时不做：

- 实时流式语音识别。
- 实时打断。
- 情绪识别。
- 紧张程度判断。
- 真实性或撒谎判断。
- 数字人实时口型同步。

如果语音能力稳定，可以增加 TTS，让面试官朗读问题。TTS 仍然属于表现层增强，不应改变核心数据和面试流程。

## 八、测试与效果证明

### 8.1 测试数据

建议准备以下内部测试数据：

- 10 份不同质量的简历。
- 30 条不同类型的面试回答。
- 10 条模糊或空泛回答。
- 10 条答非所问回答。
- 10 条包含具体项目和数据的回答。
- 10 名学生进行真实试用。

所有涉及个人信息的材料都应匿名化，优先使用自制数据或获得授权的数据。

### 8.2 建议指标

不要提前编造指标目标，先测试后填写结果。建议记录：

- 简历关键字段提取准确率。
- 岗位缺口识别准确率。
- 追问与当前回答的相关性。
- AI 评分与人工评分的差异。
- 报告生成成功率。
- 平均响应时间。
- 语音转写成功率和文字转写质量。
- 用户完成一次训练所需时间。
- 二次挑战后各维度评分变化。

### 8.3 对比实验

至少设置一个简单基线：

- 基线方案：固定题库、无简历分析、无自适应追问。
- 本项目方案：结合岗位、简历和用户回答进行追问与复盘。

比较两种方案的：

- 追问相关性。
- 用户认为建议有用的比例。
- 训练前后改进情况。
- 完成一次有效训练所需时间。

这样可以证明项目的创新点来自“上下文驱动的训练闭环”，而不是单纯使用大模型生成文字。

## 九、创新点与参赛表达

### 9.1 主要创新点

1. **从一次性问答变成训练闭环**：系统支持训练、复盘、再次挑战和前后对比。
2. **基于简历和回答的动态追问**：问题不是从题库随机抽取，而是围绕用户具体经历和回答缺口生成。
3. **可解释的 AI 评分**：评分关联回答证据、岗位要求和明确评价维度。
4. **AI生成与规则控制结合**：程序负责流程和评分计算，大模型负责理解、生成和解释。
5. **支持失败降级**：模型、文件解析或语音服务异常时，仍然能够继续完成演示流程。

### 9.2 不应作为创新点的内容

以下内容本身不能构成有效创新：

- 接入一个大模型。
- 生成一段面试问题。
- 使用聊天窗口与 AI 对话。
- 给出一个没有解释的分数。
- 使用数字人头像但没有训练闭环。

## 十、隐私、版权与安全边界

- 简历和录音属于个人信息，测试时使用匿名或自制数据。
- 用户应能删除训练记录，或至少在产品说明中写明数据保存用途。
- 公开岗位信息应保存来源链接和整理日期。
- 虚拟公司和虚拟岗位不得暗示真实公司官方合作。
- 使用第三方模型、代码、字体、图片、题库和数据集时记录来源与许可证。
- 报告中不得基于性别、年龄、地域、学校等因素评价求职能力。
- 产品定位为求职训练辅助工具，不用于真实招聘决策。

## 十一、演示流程

建议用一个具体用户故事进行 3—5 分钟演示：

1. 用户选择“Python 后端开发实习生”岗位。
2. 用户导入一份普通简历。
3. 系统指出两个岗位匹配缺口和一个项目描述问题。
4. 用户进入模拟面试，回答项目经历问题。
5. AI 根据简历项目和回答内容提出针对性追问。
6. 用户完成技术问题和场景问题。
7. 系统展示带回答证据的复盘报告。
8. 系统指出用户最需要改进的一个能力维度。
9. 用户进入第二次专项挑战。
10. 系统展示两次训练的分数变化和仍需改进的问题。

演示重点不是展示功能数量，而是让评委看到：

```text
输入真实材料
→ AI理解上下文
→ 生成相关问题
→ 根据证据评价
→ 给出改进方向
→ 再次验证改进效果
```

## 十二、MVP验收标准

只有满足以下条件，才可以认为首版核心功能完成：

- 用户可以选择一个岗位并进入训练流程。
- 用户可以通过粘贴文本完成简历分析。
- 简历分析结果包含岗位缺口和具体修改建议。
- 用户可以完成至少 5 个文字面试问题。
- 至少有一次追问明确引用用户简历或当前回答。
- 面试流程不会因为一次模型调用失败而中断。
- 复盘报告包含维度分数、回答证据和改进建议。
- 系统可以根据上一轮薄弱项生成第二次挑战。
- 两次训练可以展示可比较的指标变化。
- 录音、PDF 解析或模型异常时有明确降级路径。
- 演示账号可以从开始完整运行到报告页面。
- 产品不会展示未经依据的真实录取概率。

## 十三、后续扩展方向

以下内容属于后续版本，不应影响参赛 MVP：

- Java、前端、数据分析等更多岗位。
- 多家公司和多种面试官风格。
- 更复杂的 PDF、Word 和扫描件解析。
- 录音中的停顿、语速和填充词分析。
- TTS 面试官。
- 轻量笔试和简答题评分。
- 个性化题库和长期训练档案。
- 数字人面试官。
- 本地模型和隐私增强部署。

后续扩展的共同前提是：核心评分规则、面试状态机和训练记录已经稳定，不能先做表现层功能再补核心逻辑。

## 十四、待最终确认事项

以下内容目前是建议值，不应在开发前默认为已经确定：

1. 首版岗位是否确定为“Python 后端开发实习生”。
2. 最终采用在线 Web 演示还是本地安装包。
3. 使用哪一家主模型 API，以及是否准备备用模型。
4. 是否把语音功能加入参赛版本，还是只保留为后续增强。
5. 是否能够获得真实学生试用和匿名反馈。

在这些事项确认后，才能进一步固化产品需求、页面结构、接口定义、提示词和 Agent 任务卡。
