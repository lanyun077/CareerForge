# CareerForge 项目开发路线与验收方案

> 整理日期：2026-09-22
> 定位：从现有原型走向可靠训练产品的开发与验收路线。
> 依据：此前核对的远端版本 `985e13a`、项目方案及源码评估。
> 状态：本文是开发计划，不表示相关任务已经实现或通过验收。

## 一、产品目标与范围

### 1. 核心定位

围绕目标岗位，帮助用户找到能力缺口，并通过面试训练验证改进。

完整用户流程：

```text
输入或上传简历
→ 推荐职业方向 / 导入目标岗位 JD
→ 确认岗位与简历内容
→ 岗位匹配分析
→ 针对性模拟面试与有限追问
→ 基于回答证据的评分与复盘
→ 二次专项训练
→ 对比变化并制定下一步行动
```

产品价值集中在“发现问题、给出行动、再次验证”，而不是单纯生成题目或提供聊天窗口。

### 2. 分层交付目标

| 交付层级 | 目标 | 核心内容 |
|---|---|---|
| 可靠训练版本 | 核心闭环稳定、可演示 | 简历、岗位、面试、复盘、二轮、记录、关键异常处理 |
| 完整个人使用版本 | 支持持续训练 | 持久化、恢复训练、历史筛选、报告导出，逐步完善简历版本和推荐历史 |
| 多人试用版本 | 支持独立用户使用 | 登录、数据隔离、权限、删除机制、调用限制、部署验收 |

### 3. 范围控制

优先完善已有训练闭环，暂不把真实职位搜索、投递管理、数字人、复杂语音交互或大规模职业目录扩展作为主线。

这些能力可以在后续版本单独立项，但不应挤占训练质量、数据可靠性和使用体验的建设。

## 二、现有基础与主要差距

### 1. 现有架构判断

Next.js 前后端一体、Route Handlers、业务服务、模型调用与存储分层适合当前规模。保留现有架构，采用增量修改，暂不拆微服务、不另建后端、不引入复杂 RAG。

应保留的设计：

- 程序控制面试阶段、题数、追问上限和结束条件。
- 模型负责理解、生成和解释，后端计算最终总分。
- 统一模型客户端、输出校验和失败降级。
- 使用岗位快照保护历史训练语义。
- 通过异步 Store 接口隔离业务与存储实现。

### 2. 版本前提

整理时，本地 `main` 为 `4007a61`，已获取的远端 `main` 为 `985e13a`，本地落后 3 个提交。远端已有多岗位推荐、JD 导入、岗位快照、独立 PDF 提取、扫描 PDF OCR 和新版页面，不能重复按“尚未开发”处理。

开始执行前应重新核对版本。详细结构、操作命令和历史限制见 [AGENT_MEMORY.md](./AGENT_MEMORY.md)。

### 3. 主要差距

| 领域 | 当前需重点解决的问题 |
|---|---|
| 面试流程 | 重复提交、旧请求、刷新恢复和中途失败的行为需要系统验证 |
| 二轮训练 | 未严格排除首轮问题，报告题数描述与实际计划存在不一致 |
| 评分质量 | 结构校验不能证明引用真实或评分合理 |
| 多岗位 | 目录覆盖面不等于题库、追问和评分具有足够专业深度 |
| 数据可靠性 | 数据库切换内存不迁移历史数据，不能视为无损降级 |
| 删除与隐私 | 新增推荐记录、快照与用户隔离尚未形成完整生命周期 |
| 验证覆盖 | 早期闭环测试不能覆盖新增推荐、JD、OCR 与数据库恢复 |

以上为已有源码评估与待验证事项，不表示所有问题均已运行复现。

## 三、执行与验收原则

### 1. 任务状态

| 状态 | 含义 |
|---|---|
| 待开发 | 范围和验收条件已明确，尚未实现 |
| 已实现 | 代码完成，尚未完成全部检查 |
| 自动检查通过 | 相关构建与自动化测试通过 |
| 真实环境已验收 | 实际模型、数据库、部署或人工操作验证通过 |

不要用单一“已完成”掩盖不同验证层级。历史测试结果、mock 结果、真实环境结果分别记录。

### 2. 推进规则

1. 每阶段先确定任务边界、依赖和退出条件。
2. 修改保持小范围，不顺手重构无关模块。
3. 缺陷修复先建立复现方式，再修复并验证。
4. 每阶段形成可运行、可回退的提交，不积累跨模块半成品。
5. 按变更范围执行构建、测试和页面检查；真实环境验证随能力成熟安排，不默认全部延后。
6. 更新开发记忆、任务状态和已知限制，保留验证证据。
7. 外部资源或关键产品决策未确定时记录依赖，不以猜测替代。

## 四、阶段 0：同步代码与建立基线

**目标：** 后续开发基于同一版本，避免重复建设和错误判断。

任务：

- 检查本地修改及未跟踪文件，保护配置和已有测试材料。
- 同步到已核实的远端版本，保留新增开发文档，创建开发分支。
- 核对 Node、依赖锁文件、环境变量模板及启动说明。
- 执行构建及三模式验证：规则兜底、正常 mock、异常 mock。
- 检查推荐、JD 导入、PDF 提取、岗位快照及新版页面的实际基线。
- 建立按严重程度排序的问题清单，区分本机可验证和外部环境依赖。

**交付物：** 基线记录、问题表、可用启动说明。

**退出条件：** 构建成功；旧闭环检查通过，或阻塞已定位并解决到可以继续开发；新版功能状态清楚。

## 五、阶段 1：面试状态与二轮训练加固

### 1. 统一面试状态

前后端应一致理解：尚未开始、等待主回答、等待追问回答、回答处理中、训练完成、报告已生成。

这些状态不一定全部成为数据库字段，但必须明确每个状态允许哪些操作。

重点处理：

- 连续点击提交。
- 网络重试重复提交同一回答。
- 旧页面提交已经过期的问题回答。
- 面试完成后再次提交。
- 多标签页同时操作同一会话。

围绕会话版本或问题标识建立后端校验，不只依赖前端禁用按钮。

### 2. 恢复训练与保留输入

- 刷新后恢复当前会话。
- 记录页提供“继续训练”与“查看报告”的不同入口。
- 请求失败保留用户输入，允许重试。
- 会话丢失、已删除或不可用时说明原因和下一步。
- 明确可重试故障与必须重新开始的情况。

### 3. 修正二轮训练

- 读取首轮已问问题，优先选择未问过且关联薄弱项的题目。
- 候选不足时使用明确的退化策略。
- 统一实际题数、页面说明和报告文案。
- 开始前展示本轮训练目标。
- 先保证题库标识或规范化文本级去重，不夸大为完全消除语义重复。

**主要模块：** `interviewService.ts`、面试接口、面试页、记录页、`reportService.ts`。

**退出条件：** 重复提交不重复推进；刷新可恢复；失败保留输入；二轮优先避开首轮题目；状态和题数说明一致。

## 六、阶段 2：评分、证据与复盘可信度

### 1. 建立证据关联

为评分和追问保留必要的来源信息：问题、主回答或追问回答、引用片段、评分维度。

对模型引用进行基本核验，例如规范化空白后检查是否出现在允许引用的文本中。引用存在只能证明可追溯，不代表推理正确，后者仍需人工质量评估。

### 2. 处理不合格结果

明确处理引用不存在、建议为空、维度缺失、分数越界、内容不足等情况。对评分理由与问题无关的情形建立质量评估标准，不宣称结构校验能够完全识别语义错误。

能够按维度补齐时使用规则结果，保留模型或规则来源；无法可靠使用时整体降级。

### 3. 重组报告内容

报告回答四个问题：

1. 当前表现怎样？
2. 主要问题在哪里？
3. 下一次具体怎样改？
4. 下一轮验证什么？

主要问题按以下结构展示：

```text
问题 → 回答证据 → 对表现的影响 → 可执行动作
```

减少泛化建议，让用户能照着准备下一次回答。

### 4. 合理解释两轮变化

- 展示总分、维度分变化及具体改善证据。
- 保留仍未改善的问题。
- 标明题目及评分来源的差异。
- 尽量保持难度和评分尺度一致，不将全部涨分解释为真实能力提升。
- 固定总分公式只保证计算一致，不替代评分合理性验证。

**主要模块：** `types.ts`、`llm/validate.ts`、提示词、评分服务、报告服务及报告页。

**退出条件：** 主要结论可追溯；不合格引用有明确处理；建议可执行；比较结果不夸大。真实模型下另行验收评分与建议质量。

## 七、阶段 3：岗位与简历输入完善

### 1. 验证多岗位深度

先选 Python 后端、前端、数据分析或 Agent 开发中的三类代表方向，核对技能要求、题库、场景题、评分提示和规则关键词是否符合岗位。

建立质量基线后再扩职业数量，避免“方向更多但训练内容相同”。

### 2. JD 导入确认

- 展示解析后的名称、职责和技能要求供用户确认。
- 区分原文信息和模型整理内容。
- 不补写原文未提供的公司、薪资等信息。
- 支持修正明显解析错误。
- 确认后保存训练使用的岗位快照。
- 明确内存模式下的保存限制。

### 3. PDF 与 OCR 输入统一

- 提取后先预览，允许人工修正，再推荐或分析。
- 统一文件大小、类型、空文件和解析失败行为。
- 区分文字提取与 OCR 状态。
- 使 OCR 独立配置行为与文档一致。
- 检查超时后的资源释放及后台请求行为。
- 使用真实或自制扫描样本验证多栏、低清、旋转及混合文字图片场景。

### 4. 增加 DOCX 支持

范围限定为提取正文及必要表格文本，复用文本预览和分析流程。不承诺还原原始排版，不同时扩展旧 `.doc` 或复杂扫描文档。

**主要模块：** 岗位目录与工厂、`roleService.ts`、解析模块、简历接口与简历页。

**退出条件：** 支持的文档类型进入统一可编辑文本流程；目标岗位可确认；代表岗位训练具有差异；解析质量记录可查。

## 八、阶段 4：持久化与数据生命周期

### 1. 明确数据库故障策略

| 场景 | 建议行为 |
|---|---|
| 未配置数据库 | 明确使用演示内存模式 |
| 已配置数据库但暂时不可用 | 对依赖已有数据的操作返回可重试错误，保留输入 |
| 新建训练是否允许转内存 | 作为明确产品行为设计，不能悄悄切换并暗示已经持久化 |

暂不默认引入双写、同步队列等复杂机制。目标是明确、可恢复的故障行为。

### 2. 保存与恢复

检查 JD、简历分析、推荐结果、岗位快照、会话中间状态、报告和两轮关联。对需要原子性的关联操作按需使用事务，避免部分保存。

### 3. 定义删除语义

- 删除单次训练影响哪些数据？
- 首轮删除后二轮如何显示？
- 被多个会话引用的简历分析何时删除？
- 推荐记录如何删除？
- 岗位快照的保留与清理规则是什么？

将确定后的规则一致落实到内存与 PostgreSQL 实现。

### 4. 完善历史入口

优先提供状态、岗位、日期筛选，继续训练、关联轮次查看、删除确认和空状态。推荐历史查询在数据与删除规则稳定后增加；简历版本管理按明确使用需求继续扩展。

**主要模块：** Store 接口、两套存储实现、schema、记录接口与页面。

**退出条件：** 两套存储语义一致；故障行为明确；删除范围可解释；真实数据库读写、重启恢复及故障路径有验证记录。

## 九、阶段 5：页面体验与演示成品

在现有工作台 UI 上增量完善，不全面重写。

| 页面 | 重点 |
|---|---|
| 首页 | 训练价值、演示入口、开始训练入口 |
| 简历页 | 输入、推荐、确认岗位、匹配分析的顺序 |
| 面试页 | 题号、阶段、追问状态、输入保留、重试与恢复 |
| 报告页 | 结论、证据、行动建议、二轮入口、比较结果 |
| 记录页 | 筛选、继续训练、查看报告、删除、空状态 |

统一加载状态、禁用条件、错误提示、窄屏布局、长文本、表单标签、键盘操作与焦点。用户可理解模型降级，但不直接面对内部堆栈。

增加打印友好的报告页面，优先使用浏览器保存 PDF，确认需求后再考虑独立导出服务。

**退出条件：** 用户知道当前步骤与下一步；关键失败可恢复；桌面和移动端能完成核心流程；报告可以清晰打印或保存。

## 十、阶段 6：多人试用能力

若近期仅用于隔离环境演示，可在核心体验之后实施；若准备开放真实多用户，应提前到 DOCX、导出等扩展能力之前。

任务：

1. 选择成熟认证方案。
2. 为个人数据建立用户归属。
3. 所有查询、更新、删除检查归属。
4. 明确历史无主数据处理，不随意归属用户。
5. 为模型调用增加基本频率和输入限制。
6. 限制文件处理资源。
7. 验证未登录与跨用户访问。
8. 明确数据用途与删除入口。

认证必须覆盖后端和存储访问，不能只增加登录页面。

**退出条件：** 用户只能访问自己的数据；跨用户读取和删除被拒绝；登录后的完整训练流程通过验证；历史数据迁移方式明确。

## 十一、阶段 7：质量评估、部署与交付

测试材料和自动化应贯穿各阶段，最终在此集中完成验收与发布准备。

### 1. 验收材料

| 材料 | 内容 |
|---|---|
| 自动检查入口 | 构建、核心逻辑、mock 链路、必要的数据库集成检查 |
| 人工验收清单 | 前置条件、步骤、预期结果、实际结果 |
| 模型质量评估表 | 追问相关性、引用真实性、建议可执行性、评分合理性 |
| 问题反馈模板 | 版本、环境、复现步骤、实际结果、日志位置、严重程度 |
| 部署与恢复说明 | 环境变量、schema、启动、健康检查、回退方式 |

### 2. 固定测试材料

- 不同质量与职业方向的虚构简历。
- 明确、空泛、答非所问的回答。
- 完整与不完整 JD。
- 文字 PDF、扫描 PDF、无效文件及 DOCX 样本。
- 两轮训练对照案例。

真实材料须取得授权并适当匿名化。

### 3. 模型质量验收

人工检查追问是否抓住缺口、证据是否来自输入、建议是否可以执行、相近回答评分是否稳定、具体回答是否优于明显空泛回答，以及模型失败后的流程是否可继续。

建立固定题库基线与上下文训练的对比实验，记录结果后再表达效果，不提前编造指标。

### 4. 部署与演示

- 在目标环境完成数据库初始化、配置和部署。
- 验证重启后记录恢复、错误提示及完整训练流程。
- 多用户部署前完成认证与隔离验收。
- 准备 3—5 分钟演示脚本和无真实模型时的备用路径。
- 保存版本、配置说明、检查结果及已知限制，不记录真实密钥。

**退出条件：** 可部署、可验证、可反馈问题；核心能力具备对应证据；未通过项明确列出，不冒充已验收。

## 十二、建议实施顺序与依赖

```text
同步版本与建立基线
→ 面试状态、重复提交与恢复
→ 二轮选题与报告一致性
→ 引用核验与复盘质量
→ 数据库故障与删除边界
→ 简历预览、JD 确认、PDF/OCR 完善
→ 页面统一与报告打印
→ 多用户能力（开放试用时提前）
→ DOCX、推荐历史等扩展
→ 集中质量验收与部署交付
```

阶段编号用于组织领域，实际顺序按依赖调整：

- 基线先于所有业务改动。
- 面试状态稳定后再完善二轮与报告。
- 数据模型和生命周期明确后再扩展历史管理与认证归属。
- 真实多用户开放必须以数据隔离完成为前提。
- 自动检查、真实样本评估和文档维护贯穿全过程。
