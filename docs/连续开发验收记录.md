## 关键接口变化

- 回答：`POST /api/interview/answer` 必须传 `{ sessionId, questionId, answer }`，追问使用追问自己的 ID。相同已接收回答重试返回当前状态；旧问题的不同回答返回 409。
- 登录：`POST /api/auth` 接收邮箱密码，交给 Supabase Auth 校验；Cookie 保存访问令牌，不保存密码。`GET` 读取登录状态；`DELETE` 清除当前浏览器 Cookie。
- JD：`POST /api/roles/import` 可传 `preview: true`，返回草稿而不落库；确认时传 `confirmed` 的名称、简介、职责和技能。原直接导入 API 仍保留供已有程序调用；页面使用预览确认流程。
- 文档：`POST /api/resume/parse-pdf` 最大 15 MiB；`POST /api/resume/parse-docx` 最大 5 MiB、累计解压文本包不超过 20 MiB，拒绝旧 DOC。返回文本供编辑，不承诺排版还原。
- 推荐：`GET /api/recommendations` 返回当前用户历史，不返回简历正文；`DELETE` 清空其全部推荐记录及推荐快照。
- Store 保持异步；保存简历、会话与推荐支持关联快照一起写入。PostgreSQL 更新与查询包含 owner_id 条件。

## 删除语义（用户已确认）

删除单次训练：删除对应报告与会话快照；简历仅在没有其他训练引用时删除，同时清理简历快照。删除首轮后，已有二轮仍可单独查看，但移除对比信息与首轮关联，避免删除后仍展示首轮分数或证据。

推荐记录另行清空；清空推荐同时删除推荐快照。导入的岗位保留供后续训练复用。内存模式的全部数据随进程退出清空，不能作为持续试用的数据保障。

## 多人试用部署前置条件

1. 准备一个 Supabase 项目和至少两个独立的测试账户；目前提供邮箱密码登录，不在应用内注册或发送邀请。用户通过 Supabase 控制台管理试用账户。
2. 在目标环境配置 `AUTH_MODE=supabase`、`SUPABASE_URL`、`SUPABASE_ANON_KEY`、`DATABASE_URL`。不将数据库密码或 service-role key放入前端；这里使用的 anon key 只用于 Auth 协议。
3. 备份数据库后执行 `db/schema.sql`。六张表新增 nullable owner_id 和索引，启用 RLS，不添加 anon/authenticated 的表访问策略。服务器数据库连接需要具有服务端表访问权限；应验证 Supabase 公共 REST 角色无法直接读取表。
4. 历史 owner_id 为 NULL 的数据默认不可见，不自动归属给首个账户。确认归属后才可在备份与审核下迁移；本次没有改写历史用户数据。
5. 使用 HTTPS；确认登录 Cookie 带 Secure、HttpOnly、SameSite=Lax。当前 access token 最长保存一小时，到期需重新登录；面试页保留输入并支持新页面登录后重试。
6. 按下面的真实验收清单验证，再决定开放试用。配置模式徽章不证明认证、数据库或模型能连通。
